# 首次冻结测试结果与后续研究任务

## 测试边界

- 模型版本：`debugpath-stage2-2026-09-11`
- 测试集：14条首次运行的公开确认案例，每个候选原因1条
- 对比策略：不追问、固定顺序、随机追问、纯信息增益、完整可回答性感知策略
- 公平条件：相同初始混合检索、相同答案、最多4次追问、相同稳健停止规则
- 原始结果：`data/evaluation/frozen_test_results.json`

协议、模型和测试集在运行前均已通过指纹校验。结果文件只生成一次，后续调用只读取首次结果。

14条案例中有5条未能被入口识别为现有故障族，均按端到端失败计入全部策略。因此，当前Top-1同时反映“能否进入正确诊断场景”和“进入后能否定位原因”，不能只解释为选问算法准确率。

## 能够支持的结论

1. 主动询问具有实际作用。不追问为50.0%，三种确定性交互策略均为64.3%。
2. 信息增益提高了追问效率。相同Top-1下，信息增益平均追问2.07次，固定顺序为2.36次。
3. 稳健停止比较保守。完整策略只对4条案例给出“证据充分”的确定判断，这4条全部正确，且没有错误自信停止。
4. 入口识别是当前最明显的端到端瓶颈。5条失败涉及模块遮蔽、驱动异常、macOS MPS、容器内服务地址和本地服务未启动等自然语言变体。

## 暂时不能声称的结论

- 不能声称系统真实环境准确率为64.3%；测试集只有14条，每类原因只有1条。
- 不能声称完整策略优于纯信息增益；两者在本次测试中的所有汇总指标相同。
- 不能声称风险项已经产生效果；本次实际选择的问题累计风险均为0。
- 不能用这14条案例继续调参后，再把同一结果当作无偏测试成绩。

## 下一版研究任务

### 1. 改进故障族入口检索

把当前依赖固定词串的场景识别改为可解释的候选故障族检索：综合错误码、包名、平台、服务名和BM25证据分数，输出Top-k故障族及依据。已查看的5条失败案例只能进入下一版开发集；改进后需要另建新的外部测试集。

### 2. 扩展服务感知因果图谱

增加`Service`、`Endpoint`和`DeploymentContext`节点。先确定实际服务、地址和部署位置，再选择对应检查与修复，例如区分Ollama的`/api/tags`检查与Neo4j驱动连通性检查，避免“原因正确但检查对象错误”。

### 3. 让完整策略与纯信息增益形成可验证差异

通过真实交互记录估计问题可回答率和检查成本，补充具有非零风险的检查节点。比较两种策略在追问数、“不清楚”次数、成本、风险和证据充分覆盖率上的差异，而不是只看Top-1。

### 4. 扩大独立测试并报告不确定性

新建不与开发集和本次冻结集重复的外部测试集，增加每类原因样本数；报告分故障族结果、置信区间和配对差异，避免由单条案例决定一类原因的结论。

### 5. 完善动态图谱展示

每轮只突出实际参与推理的节点与边：当前故障、候选原因、当轮问题、用户观察及其概率影响。结束时再展开检查、修复、风险和来源路径，使“子图如何随证据变化”能够被直接讲清楚。
