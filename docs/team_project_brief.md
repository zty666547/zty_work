## 小组项目介绍与自主开发说明

## 一、我们要做什么

本次知识工程实践项目计划完成一个**面向实际应用的高完成度原型系统**：让人工智能专业学生能够使用自然语言查询培养方案、课程安排和培养要求，并通过知识图谱查看答案所依据的课程关系。

项目当前以《2023级人工智能专业培养方案》为主要数据来源，采用 Graph RAG（知识图谱增强检索生成）技术路线。最终成果不声称已经达到学校正式部署或教务系统替代品的标准，但应当具有完整的交互形式、清楚的使用场景和继续落地的潜力。

一句话概括：

> 我们希望把内容复杂、查询不便的专业培养方案，转化成一个学生可以直接提问、能够查看依据的智能问答原型系统。

项目仓库：[zty666547/zty_work](https://github.com/zty666547/zty_work)

## 二、为什么选择这个题目

培养方案通常以较长的文字和课程表格呈现。大一至大三学生在实际学习过程中，可能会遇到以下问题：

- 不清楚某门课程在第几学期开设、属于必修还是选修；
- 难以快速统计某学期或某类课程的学分与课程数量；
- 不容易理解课程、学期、课程类别、开课单位和毕业要求之间的关系；
- 想规划后续学习方向，但无法从整份培养方案中快速找到相关信息；
- 普通大模型可能给出听起来合理、却不符合本校培养方案的答案。

知识图谱适合表达课程之间以及课程与培养要求之间的结构化关系；RAG 可以让大模型基于检索到的真实材料回答，并展示来源。因此，本项目既符合知识工程实践课程的技术要求，也具有明确的实际应用场景。

## 三、预期使用效果

最终系统将尽量以一个小型产品的形式呈现，而不只是运行几条命令。学生可以打开网页并提出问题，例如：

- “知识工程是多少学分，建议在哪个学期修读？”
- “第四学期有哪些专业核心课？”
- “第六学期有哪些专业选修课？”
- “人工智能专业有哪些毕业要求？”
- “这门课程属于必修课还是选修课？”

系统尽量提供以下内容：

- 基于培养方案生成的自然语言答案；
- 课程名称、学分、学期、课程类别等结构化信息；
- 与问题有关的知识图谱关系；
- 答案所使用的来源和证据；
- 当前适用的培养方案版本提示；
- 在资料不足时明确表示无法确认，避免无依据地编造答案。

目前知识库只对应 **2023级人工智能专业培养方案**。不同年级可能执行不同版本，因此项目不会把当前数据直接当作所有年级的正式选课规则。后续如能取得其他年级资料，可以继续扩展。

## 四、当前项目基础

目前仓库已经具备一个可继续开发的基础版本，主要包括：

- 培养方案知识图谱的数据结构；
- 课程、学期、课程类别、开课单位和毕业要求等实体与关系；
- 中文课程名称、简称和学期俗称的查询支持；
- 图谱证据检索与离线回答；
- DeepSeek 问答链路的接口；
- 基于 Streamlit 的学生端交互页面；
- 数据校验、基础测试和少量检索评测问题；
- Neo4j 图数据库与无需外部服务的离线演示方式。

这个版本是大家共同探索的起点，不代表所有设计已经确定，也不要求每个人沿着完全相同的方向开发。

## 五、建议的协作方式

本项目采用“**共同基线、独立探索、最后汇总**”的方式。

每位成员可以根据自己的兴趣和能力，从当前仓库出发，独立选择一个方向进行尝试。开发过程尽量放在个人分支中，不直接覆盖主分支。最后由负责人统一查看各成员成果，选择其中运行稳定、思路清楚、对答辩有价值的功能或创新点，整合进最终版本。

这样做的目的不是要求每个人完成相同任务，而是让不同想法能够并行尝试，降低多人同时修改同一部分造成的沟通和合并成本。

推荐的基本流程：

1. 从当前主分支获取最新版本；
2. 建立自己的独立分支；
3. 选择感兴趣的改进方向，自主设计和实现；
4. 保留清楚的阶段性提交记录；
5. 在提交成果时说明“解决了什么问题、如何演示、还有什么限制”；
6. 最终由负责人统一测试、比较并决定是否整合。

个人分支可以使用类似下面的名称：

```text
feature/姓名或昵称-改进方向
```

例如：

```text
feature/zhangsan-ui
feature/lisi-retrieval
feature/wangwu-visualization
```

开发时请不要把 DeepSeek API Key、Neo4j 密码或其他个人凭据提交到 GitHub。

## 六、可以自主探索的方向

以下方向仅供参考，不是强制分工。每个人可以选择其中一项，也可以提出自己的想法。

### 1. 页面与交互体验

- 优化网页布局、配色和项目介绍；
- 增加常见问题和一键示例；
- 改进答案、证据和知识图谱的展示方式；
- 增加培养方案版本选择或用户反馈入口。

### 2. 数据与知识图谱

- 补充和核对课程数据；
- 改进实体类型、关系类型和属性设计；
- 增加课程方向、知识领域等新的关系；
- 尝试导入其他年级的培养方案，同时严格区分版本。

### 3. 检索与问答

- 改进课程别名、简称和模糊匹配；
- 支持更复杂的多条件或多跳问题；
- 比较不同图检索、向量检索或混合检索方法；
- 优化无答案判断，减少大模型幻觉。

### 4. 可视化与学习路径

- 展示课程与学期之间的关系；
- 生成某个学习方向的课程路径；
- 优化局部知识图谱的交互展示；
- 设计更适合答辩演示的可视化页面。

### 5. 测试与评价

- 设计更多真实学生问题；
- 建立单跳、多跳、组合条件和知识库外问题测试集；
- 对比不同检索方式的正确率、证据命中率和响应效果；
- 记录典型错误，并提出改进方案。

### 6. 文档与答辩表达

- 完善系统架构图、数据流程图和知识图谱 Schema；
- 记录开发过程与关键设计选择；
- 整理演示脚本、答辩 PPT 或常见提问；
- 从学生视角设计真实使用案例。

## 七、参与方式与最低共识

是否进行独立开发，可以由个人根据时间和兴趣决定，不作强制要求。没有参与开发的成员，后续也会预留必要时间，由负责人统一讲解最终成品、演示流程、核心技术和答辩内容。

如果选择参与开发，希望至少做到：

- 独立完成自己选择的尝试，不依赖其他成员实时配合；
- 不直接破坏当前可以运行的基础版本；
- 对使用 AI 生成的代码进行基本阅读和验证；
- 提交一个能够说明或演示的结果，而不是只提出概念；
- 主动说明成果的优点、限制和是否适合合并。

如果暂时不参与开发，建议在答辩前了解以下基础内容：

- 项目为什么选择培养方案问答场景；
- 知识图谱、检索和大模型分别承担什么作用；
- 系统如何根据培养方案回答并展示依据；
- 当前原型的适用范围和不足。

## 八、成果如何汇总

最终版本不会机械地把所有分支全部合并。负责人会主要根据以下标准筛选成果：

- 是否符合培养方案问答的真实使用场景；
- 是否能够稳定运行和现场演示；
- 是否体现知识工程或 Graph RAG 的价值；
- 是否有明确的改进效果或创新点；
- 是否能在答辩中解释清楚；
- 是否会增加过高的运行风险或维护成本。

未进入最终版本的探索也不代表没有价值。只要过程清楚、结论可信，它仍然可以作为方案比较、失败经验或后续工作写入报告。

## 十、项目最终定位

我们追求的不是在短时间内完成一个已经能够正式投入学校使用的成熟产品，而是：

> 从真实学生需求出发，完成一个可运行、可交互、可解释的 Graph RAG 应用原型，并通过实际演示证明它具有继续完善和落地的价值。

最终交付可能仍存在数据覆盖不完整、部分问法支持有限、尚未正式部署等不足。我们会如实说明这些边界，同时优先保证核心链路完整、现场演示稳定、项目思路清楚。

欢迎大家根据自己的兴趣自由尝试。任何经过验证的优秀功能、创新思路、测试结果或表达方式，都可能成为最终项目的一部分。
