# 第二阶段因果参数校准

## 本轮依据

真实开发集暴露出两类稳定混淆：

- 两条“无兼容wheel”的案例中，目标包都不可见；原图却把“包可见”对版本不兼容的条件概率设为0.80，方向过强；
- 两条跨宿主机或容器的地址错误案例都满足“服务所在机器本机可达”，而两条服务停止案例都不满足。原来的“当前地址健康检查”无法表达这个差别。

## 修改

1. 将“包可见｜Python版本不兼容”从0.80调为0.25。0.25来自两条开发观察在拉普拉斯平滑后的估计，避免把小样本当成绝对规律。
2. 新增“目标主机本机检查是否成功”问题，并连接到5个服务配置原因。地址错误、服务停止、端口冲突和认证状态的条件概率同样采用小样本平滑值；没有直接观察的环境变量缺失保持0.50中性值。

这不是简单增加关键词：新问题会参与期望熵和信息增益计算，只有当前候选分布认为它有价值时才会被选择。用户回答后，它通过图谱中的条件概率改变候选原因分布。

## 开发集消融

运行：

```bash
python scripts/evaluate_calibration.py
```

脚本分别测试修改前、仅概率校准、仅新增问题、两项合并，防止把多个变化的效果混在一起。所有数字都来自28条已查看开发案例；冻结测试集为空，因此只能用于选择方案，不能作为最终性能结论。

## 已知边界

“Python版本不兼容”同时包含“安装阶段没有兼容wheel”和“包已安装但运行时不兼容”两种情形，单一条件概率仍然是折中。若后续新案例证明两种模式差异稳定，应将其拆成两个更具体的原因节点，而不是继续把一个概率调到极端。

## 参数冻结

本轮选择完成后，`data/evaluation/model_freeze.json`固定图谱内容指纹和12项检索、选问、停止参数。冻结测试集的最低目标是14条，即每个候选原因至少1条全新来源；收集期间不得用这些案例反向修改图谱或参数。可运行`python scripts/audit_model_freeze.py`确认工作区没有偏离冻结版本。
