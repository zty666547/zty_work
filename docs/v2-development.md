# DebugPath 第二版开发说明

## 为什么开始第二版

第一版冻结测试的14条案例中，有5条在进入主动诊断前就因固定词串未命中而失败。它们对应的图谱证据其实已经存在，问题在于入口只检查故障名称、别名和示例，没有利用证据检索结果。

## 当前新增：可解释故障族检索

第二版入口并行计算两类信号：

```text
用户故障描述
  ├─ 固定特征匹配：错误码、标准异常名、明确别名
  └─ BM25证据检索：证据片段 → 候选原因 → 所属故障族
                         ↓
                 汇总并输出Top-k故障族
```

当前开发公式为：

```text
故障族得分 = 55% × 固定特征得分 + 45% × 图谱证据得分
```

若没有固定特征命中，仍可完全依靠证据路径给出候选故障族。每个候选项会保留命中特征、证据片段、证据支持的原因和分项得分，因此路由过程可以解释和展示。

路由不会对所有输入强行分类，而是给出三种状态：

- `routed`：首位证据明确，进入对应故障族的动态诊断；
- `ambiguous`：前两类得分过近，返回一个跨故障族澄清问题；
- `unsupported`：没有足够证据，提示用户补充组件名称和完整报错。

第二组案例已经被用于发现第一版缺陷，现在只能充当第二版开发反馈。该结果说明新组件修复了已知入口失败，不能证明它对全新数据仍有100%准确率。

## 版本隔离

- 第一版核心引擎、服务、图谱、BM25和参数保持冻结；
- 新入口位于`src/retrieval/issue_router.py`，正式网页默认使用第二版诊断服务；
- `DiagnosisServiceV2`会把明确路由结果转换为初始候选原因状态；若前两类得分过近，网页先让用户在两个候选故障族之间澄清，再继续同一条动态诊断链；
- 第一版冻结产物与审计脚本保持不变，第二版通过独立服务、图谱叠加层和演示轨迹继续开发；
- 第二版完成后必须重新收集未见外部测试集。

## 网页完整流程

1. 用户输入故障描述，页面展示故障族候选、固定特征和图谱证据得分；
2. 若入口有歧义，用户只需在前两个候选故障族中确认一个方向；
3. 系统进入主动诊断，每次回答后同步更新候选概率和当前子图；
4. 子图按实际推理过程展示故障、证据、原因、问题、观察、服务、端点和部署环境；
5. 满足稳健停止条件后，只沿最终原因展开检查、修复、风险和来源路径。

## 下一步

1. 将服务感知路径扩展到Neo4j、vLLM和远程服务器；
2. 为不同检查动作收集真实耗时、风险和用户可回答率，校准效用函数；
3. 收集新的未见案例，在不再调参的前提下验证故障族路由、追问效率和最终根因排序。

Open WebUI容器访问宿主机Ollama的第一条完整路径已经接入第二版服务。新图谱共有144个节点、366条关系；固定案例经过两次有效回答后，将“服务地址配置错误”提升到93.3%，并输出Ollama `/api/tags`检查与`OLLAMA_BASE_URL`修复。详细结构见[服务感知因果图谱](service-aware-graph.md)。

## 信息增益优化进度

第二版开发分析中，42条已查看案例有16条的首问因可回答率和成本修正而改变。完整策略在原28条开发案例和已查看的14条案例中均保持100% Top-1，但风险项尚未被实际触发。详细结果和适用边界见[第二版信息增益策略分析](v2-information-gain.md)。
