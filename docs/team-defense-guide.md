# DebugPath 小组答辩速查手册

这份文档用于帮助没有深度参与开发的组员快速了解项目，并统一答辩口径。回答老师问题时，以当前仓库实际实现为准，不扩大实验结论。

## 一、30秒项目介绍

DebugPath 是一个面向 AI 开发环境故障的交互式诊断 Graph RAG。系统先从文本证据和因果知识图谱中检索候选原因，再选择信息增益最高的问题。用户每回答一次，系统就使用贝叶斯公式更新原因概率，并重新选择下一问。达到停止条件后，系统沿图谱生成包含前置检查、检查命令、修复建议、风险等级和证据来源的方案。

一句话版本：

> DebugPath 让知识图谱随着用户回答逐轮收敛，而不是根据第一次输入直接猜测答案。

## 二、项目解决什么问题

一条开发环境报错经常对应多个原因。例如“PyTorch 检测不到 GPU”可能来自驱动、PyTorch 构建、CUDA 版本、容器映射或操作系统。用户第一次输入的信息通常不足，普通问答容易返回一长串通用建议。

DebugPath 把诊断过程拆成连续步骤：

```text
用户输入报错
  → 识别故障场景
  → 检索证据和候选原因
  → 选择信息增益最高的问题
  → 用户回答
  → 更新原因概率和候选子图
  → 继续询问或停止
  → 输出可验证、可追溯的排查方案
```

当前图谱包含三个故障场景：

1. Python 模块无法导入；
2. PyTorch 无法使用 GPU；
3. 服务或配置连接失败。

网页提供四条示例输入，其中 API 401 与 Neo4j Connection refused 都属于第三个故障场景。

## 三、老师要求的三个部分

### 1. 知识图谱构建

系统用固定 Schema 表达故障诊断知识。目前定义了12类实体和15类关系。

主要实体包括：

- `Issue`：用户感知的故障；
- `Cause`：可能原因；
- `DiagnosticQuestion`：系统提出的问题；
- `Observation`：用户可以确认的现象；
- `DiagnosticCheck`：只读或低副作用检查；
- `RepairAction`：满足前置检查后可以采用的修复；
- `Risk`：操作风险；
- `DocumentSource`、`EvidenceChunk`：证据来源和可检索片段。

核心关系是：

```text
故障 → 可能原因
故障 → 诊断问题 → 观察结果 → 原因
原因 → 检查步骤
原因 → 修复操作 → 前置检查与风险
原因、检查、修复 → 官方来源
证据片段 → 支持的原因、检查或修复
```

构建程序会检查实体类型、关系类型、关系方向、重复项和端点完整性。相同输入会生成稳定排序和相同内容指纹，可写入内存图，也可导入 Neo4j。

当前图谱规模：

- 132个节点；
- 345条关系；
- 30条可检索证据片段。

### 2. 检索与动态推理

这是项目的重点，分为初始检索和主动检索两个阶段。

#### 初始检索

1. 使用故障名称、别名和示例识别当前 `Issue`；
2. 从图谱读取该故障连接的候选原因和启发式先验；
3. 使用 BM25 检索最相关的5条 `EvidenceChunk`；
4. 沿 `CHUNK_SUPPORTS_CAUSE` 把证据得分映射到原因；
5. 按45%文本证据和55%图谱先验形成初始概率。

#### 主动检索

系统对每个未询问的问题计算：

```text
IG(q) = 当前熵 - 回答该问题后的期望熵
Utility(q) = IG(q) - 0.02×检查成本 - 0.05×风险成本
```

系统选择效用最高的问题。用户回答后，根据图谱中的条件概率执行贝叶斯更新：

```text
新概率 ∝ 原概率 × 当前回答在该原因下出现的可能性
```

回答“无法确认”时不修改概率，但该问题会被记录为已经问过。

停止条件包括：

- 至少询问两轮后，最高候选达到78%；
- 达到最多4轮询问；
- 没有剩余问题；
- 剩余问题的信息增益低于0.01；
- 用户主动结束。

动态检索的含义不是修改底层知识图谱。底层节点和关系保持不变，变化的是当前候选原因概率、当前观察、下一问和需要展示的候选子图。

### 3. 受控知识注入

系统不会让大模型自由编写技术结论。

程序先将验证通过的诊断项转换为 `C1/C2/C3` 声明白名单，并保留本轮召回的 `E001...` 证据编号。DeepSeek 只能：

- 调整声明的展示顺序；
- 选择已经召回的证据；
- 选择 diagnosis、checks 或 safety 侧重点。

DeepSeek 不能新增原因、命令、修复操作或链接。程序会拒绝未知ID、遗漏声明、重复证据和非法结构。验证失败时，系统自动使用确定性离线模板。

最终方案还会检查：

- 修复是否具有前置检查；
- 是否标注风险等级；
- 是否存在来源；
- 是否包含危险命令模式；
- 高风险操作是否已经被阻止。

## 四、当前已经完成的功能

- 从结构化数据重复构建相同知识图谱；
- 离线运行，不依赖 Neo4j 或大模型；
- BM25 文本证据召回与图谱先验融合；
- 基于信息增益和风险成本主动选问；
- 根据用户回答进行贝叶斯概率更新；
- 左侧问答、右侧候选子图同步变化；
- 逐轮回看问题、回答、排名、概率、熵和停止原因；
- 下载完整诊断轨迹 JSON；
- 生成包含检查、修复、风险和来源的方案；
- 可选导入 Neo4j 并检查节点与关系规模；
- 可选使用 DeepSeek 对白名单内容进行受控编排；
- 当前自动化测试共32项，全部通过。

## 五、演示案例需要记住什么

推荐统一使用“PyTorch 检测不到 GPU”案例。

```text
初始：驱动不可用 47.8%，容器未获得GPU 11.8%

回答1：nvidia-smi 正常
结果：驱动降到7.3%，CPU版PyTorch升到50.4%

回答2：程序在容器中运行
结果：容器未获得GPU升到72.1%

回答3：torch.version.cuda不是None
结果：容器未获得GPU升到85.2%，达到停止阈值
```

最后展开的图谱路径是：

```text
PyTorch无法使用GPU
  → 容器未获得GPU设备
  → 检查容器GPU映射
  → 为容器启用GPU
  → 风险等级
  → 官方证据来源
```

候选节点不会直接删除。概率下降的节点变灰，当前首位变绿，节点大小随概率变化。

## 六、实验结果与正确表述

### 选问策略实验

| 策略 | Top-1 | 平均追问 | 3问内成功 |
| --- | ---: | ---: | ---: |
| 不追问 | 73.3% | 0.00 | 73.3% |
| 固定顺序 | 96.7% | 3.43 | 36.7% |
| 随机追问 | 97.4% | 3.32 | 45.0% |
| 信息增益 | 100.0% | 2.83 | 70.0% |

正确结论：在当前知识库和30条来源约束的合成路径中，主动询问补足了初始描述的信息缺失；信息增益策略在保持定位结果的同时减少了平均提问次数。

不能说：系统在真实环境中的诊断准确率达到100%。

### 组件消融实验

当前实验还显示：仅BM25、不追问时的Top-1为76.7%，图文融合、不追问时为73.3%。这说明当前人工图谱先验尚未充分校准，固定融合权重没有优于仅文本检索。主动询问才是当前结果提升的主要来源。

这不是需要隐瞒的缺点，而是可以说明项目发现了明确的后续研究问题：使用独立真实案例校准先验概率和融合权重。

### 知识注入边界测试

- 9次合法编排全部接受；
- 24次非法编排全部拒绝；
- 该结果验证程序白名单边界，不等于开放式大模型安全性达到100%。

## 八、老师可能提出的问题

### 问题1：这个项目到底是不是 Graph RAG？

建议回答：是。系统使用知识图谱限定候选原因和关系路径，同时检索图谱中的证据片段，再把检索结果用于诊断和答案生成。与普通 Graph RAG 的区别是，我们没有停在一次性检索，而是让用户回答触发新的概率更新和候选子图检索。

### 问题2：项目最主要的创新在哪里？

建议回答：主要特色在检索推理层。系统根据当前候选概率计算问题的信息增益，主动获取最有区分度的新证据，然后通过贝叶斯更新重新排序图谱节点。创新重点不是图谱规模，而是可解释、可回放的动态诊断过程。

### 问题3：主动询问属于检索还是推理？

建议回答：它同时包含两者。信息增益和贝叶斯更新属于推理；推理结果又决定下一轮进入图谱的方向和需要取出的候选子图，因此整体可以称为主动检索或检索推理闭环。

### 问题4：为什么不直接让大模型继续问问题？

建议回答：自由生成问题难以保证稳定性，也无法解释为什么选择这个问题。当前系统只从图谱中已有的问题集合选择，并展示信息增益、成本和风险，因此相同状态会得到相同问题，也便于实验比较。

### 问题5：BM25 在系统中负责什么？

建议回答：BM25只负责初始文本证据召回。它搜索30条EvidenceChunk，再通过图谱关系把证据映射到候选原因。后续收敛主要由主动询问和贝叶斯更新完成。

### 问题6：为什么使用 BM25，没有使用向量数据库？

建议回答：当前知识库较小，错误码、包名和命令等精确词很重要，BM25离线、可复现且容易解释。向量检索可以作为后续扩展，但期中阶段优先验证动态诊断机制，而不是堆叠检索组件。

### 问题7：图谱概率从哪里来？

建议回答：`HAS_POSSIBLE_CAUSE.prior` 保存启发式先验，`OBSERVATION_SUPPORTS.p_yes_given_cause` 保存条件概率。它们目前用于原型排序，并未经过大规模真实案例校准，所以我们把概率解释为排查优先级，不解释为客观准确率。

### 问题8：为什么使用信息增益？

建议回答：诊断的目标不是马上选择当前第一名，而是用尽量少的问题区分候选原因。信息增益衡量一个问题预计能够减少多少不确定性，再结合检查成本和风险，就能优先选择既有区分度又容易执行的问题。

### 问题9：用户回答后发生了什么？

建议回答：系统根据这个回答在不同原因下出现的条件概率，对所有候选原因执行贝叶斯更新，然后归一化。更新后的概率决定新的排名、节点大小和颜色，同时影响下一问。

### 问题10：动态图谱是不是每轮重新构建？

建议回答：不是。底层图谱保持不变。系统每轮更新诊断状态，并从完整图谱中取出与当前故障、问题、观察和候选原因相关的子图。动态图展示的是检索焦点和概率变化。

### 问题11：Neo4j 在项目中有什么作用？

建议回答：Neo4j用于持久化、查询核验和图谱展示。核心诊断算法可以基于相同图谱产物在内存中离线运行，因此现场没有数据库网络也能稳定演示。不能说信息增益和贝叶斯更新由Neo4j完成。

### 问题12：DeepSeek 在项目中有什么作用？

建议回答：DeepSeek只负责受控编排，不决定原因概率，也不能生成新的技术事实。程序提供声明和证据白名单，模型只能调整已有内容的顺序和侧重点，失败时回退到离线答案。

### 问题13：你们如何避免幻觉？

建议回答：原因、检查、修复和来源都来自结构化图谱；生成前进行计划验证；大模型只能引用白名单ID；未知ID、遗漏声明和非法结构会被拒绝；最终还保留确定性离线模板。

### 问题14：为什么实验中的信息增益策略达到100%？

建议回答：因为测试路径与当前知识库共享同一受控原因和观察空间，所以结果证明算法在当前封闭环境中可以收敛。案例是来源约束的合成路径，并非独立真实用户日志，因此不能将100%解释为真实环境准确率。

### 问题15：图文融合为什么没有超过仅BM25？

建议回答：消融实验说明当前人工先验和固定45%融合权重尚未校准，部分场景中会拉低初始排序。这是当前系统的真实局限。后续需要只在真实开发集上校准先验与融合权重，再用独立测试集验证。

### 问题16：项目目前最大的不足是什么？

建议回答：知识范围仍小，只有三个故障场景；场景识别主要依赖别名匹配；概率参数缺少真实案例校准；实验以合成路径为主。这些都属于下一阶段需要补强的部分。

### 问题17：为什么不扩大知识图谱规模？

建议回答：期中阶段先保证一条诊断链完整可运行，并验证动态检索相对于静态回答的作用。盲目增加节点不能证明推理能力。机制稳定后，再增加真实案例和故障范围。

### 问题18：下一步准备做什么？

建议回答：收集独立、脱敏的真实故障对话；划分开发集和测试集；只在开发集校准概率和融合权重；在测试集报告各故障族结果、置信区间、证据召回率、方案覆盖率和响应时间；最后完成Neo4j Aura展示。
